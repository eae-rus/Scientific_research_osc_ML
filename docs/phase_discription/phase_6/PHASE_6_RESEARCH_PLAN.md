# Фаза 6. План обработки папок и составления отчётов

Версия 0.6 для обсуждения, 9 октября 2026 года.

Ближайшая цель — воспроизводимый проход по папкам документов с подготовкой качественных сопоставимых отчётов. Начинаем с небольшого локального пилота; затем переносим проверенный процесс на корпус. Поиск интересных групп и анализ сигналов будут следующими задачами. Тип события заранее не назначаем.

Этот файл задаёт порядок работ. [Инструкция](PHASE_6_EXTRACTION_PROMPT_DRAFT.md) задаёт правила и форму отчёта; [словарь](PHASE_6_TERMINOLOGY_DRAFT.md) — формулировки; [наблюдения по примерам](PHASE_6_RESEARCH_NOTES.md) — историю чтения и полезные находки. Четыре согласованных образца находятся в [reports](reports/). Отдельные планы под каждый риск не создаём. Точные исходные тексты с 14 новыми примечаниями сохранены в закрытом аудите `private/phase6_review/2026-10-08-future/oct09_phase6_review.json`.

## 1. Цепочка работ

Подготовка структуры «год → папка комплекта» → машинный учёт файлов и постоянные ID → агентское чтение одной папки → отчёт с источниками и поисковыми тезисами → проверка специалистом → повторяемые проходы по корпусу.

Папка — единица запуска, но не обещание одного физического события. Внутри могут быть эпизоды, редакции и разные точки наблюдения. Подтверждённая завершённая справка имеет приоритет для основной сводки; существенные изменения оценок сохраняются. Файл, найденный рядом, ещё не подтверждает связь с эпизодом.

## 3. Что уже подготовлено в коде

Модуль `osc_tools/corpus/case_inventory.py` работает на стандартной библиотеке Python. Определение формата по имени вынесено в `osc_tools/io/format_detection.py` и переиспользуется загрузчиком осциллограмм. Учёт не загружает сигналы и не читает содержание документов.

Две команды из корня проекта:

```powershell
python -m osc_tools.corpus.case_inventory scan --root "Вордовские файлы, примеры" --output "private/phase6_review/2026-10-08-future/corpus_inventory.json"
python -m osc_tools.corpus.case_inventory plan --root "Вордовские файлы, примеры" --output "private/phase6_review/2026-10-08-future/normalization_plan.json"
```

Используется Python среды проекта либо доступный bundled Python; команды не устанавливают зависимости. Обе команды только читают исходники и сохраняют JSON вне корпуса. При повторном `scan` в тот же файл сохраняется существующий реестр ID. Этот файл нужно хранить, а не строить каждый раз с нуля. Для другого корпуса задаётся другой результат.

На текущих примерах: 11 подготовленных папок и 6 отдельных документов в корне года. План размещения содержит 4 группы `ready` и 2 `needs_review`: имена перед расширением заканчиваются пробелом, который Windows может нормализовать. Автоматически обрезать имя не стали; правило переименования нужно задать явно. Применение плана доступно отдельной функцией `apply_normalization_plan`, в CLI команды применения нет. На исходном корпусе функция не запускалась.

Проверены 11 тестов стандартной библиотекой: устойчивость ID, компоненты записей, архивы без распаковки, ограничения путей, изменившиеся источники, конфликт имён, сохранность байтов, откат при ошибке, конечный пробел. Интеграционные тесты полного загрузчика сигналов в этой среде не запускались: отсутствуют `polars` и `pytest`. Перенос детектора сохраняет прежние имена импортов, но это не заменяет интеграционной проверки.

Ограничения первого учёта: ZIP просматривается по списку, без извлечения; для 7z/RAR нужны необязательные библиотеки, сейчас они отсутствуют. Комплектность многотомного архива и совпадение упакованного содержимого с распакованным не проверены. CFG/DAT связываются по имени как кандидаты, без проверки каналов и времени. Совпадение хешей означает побайтовый дубль файла, а не тождество всего события. Изменение структуры или переименование папки требует явного обновления реестра — автоматического угадывания по похожести пока нет.

## 4. Имена, хранение и повторный проход

Универсальное имя нового отчёта: **`case_000001__report.md`**. Шесть цифр обеспечивают простую сортировку; номер — постоянный ID комплекта, а не номер после текущей сортировки каталогов. В имени нет года, объекта, диагноза, модели или статуса. Новая более ранняя папка получает следующий свободный ID, существующие не перенумеровываются. Хронологический отбор делается по закрытому реестру, а не имени файла.

Реестр связывает `case_id` с исходной папкой. Имена прежних G03/G04/G07/G12 оставлены для согласованных образцов; они не являются правилом нового корпуса. G07 уже соответствует `case_000006`, G12 — `case_000011` текущего машинного учёта. D020 получит самостоятельный ID после подготовки его папки. Алиасы Gxx и Dxxx при запуске необходимо сохранить явно, без переименования первичных источников.

Для пилота достаточно общего манифеста и одного Markdown на папку. Следующим шагом добавляется машинный результат/журнал запуска в каталоге результатов того же ID: версия инструкции и словаря, модель и настройки, если известны, входные хеши, прочитанные источники и локаторы, состояние и ошибки. Не создаём отдельный Markdown-документ на каждую служебную операцию.

Будущие состояния очереди: `queued`, `running`, `draft`, `partial`, `reviewed`, `failed`. Принятие специалистом отличается от успешного завершения программы. При изменении исходников сохраняется новая редакция результата и причина пересмотра; прежняя принятая версия не исчезает. Правила очереди и повторного запуска пока описаны, не реализованы.

## 5. Как пробовать локальную открытую модель

На этой машине обнаружена RTX 3060 Ti с 8 ГБ VRAM и CLI LM Studio. Объём RAM, установленные модели, их лицензии, доступный контекст, поддержка изображений и устойчивость вызовов инструментов пока не установлены. Наличие CLI не подтверждает готовность модели. В этом проходе модель не скачивалась и не загружалась для анализа.

Первый путь — проверить уже установленное в LM Studio и провести маленький текстовый пилот. Выбор конкретной модели и квантования делается после этой проверки и замера памяти, скорости и качества. Для 8 ГБ нельзя заранее обещать нужную полноту чтения, большой контекст или качественный просмотр схем. Разбор длинных источников должен сохранять локаторы и историю чтения, а не полагаться на помещение всей папки в один контекст.

Сервер модели и агент — разные части системы: модель предлагает вызов инструмента, программа выполняет допустимую операцию и возвращает результат. Такой цикл описан в [документации LM Studio](https://lmstudio.ai/docs/developer/openai-compat/tools); альтернативный сервер может использовать [вызовы инструментов Ollama](https://docs.ollama.com/capabilities/tool-calling). Смена сервера не создаёт поддержку старого DOC, архивов или зрения. Программный интерфейс сервера ещё не доказывает, что выбранная модель надёжно использует его.

Минимальные инструменты хоста:

| Инструмент | Возвращаемый результат |
|---|---|
| `get_manifest` | Учёт текущей папки, ID файлов и известные ограничения |
| `read_document(file_id, locator)` | Выбранный текст/таблица со способом извлечения и локатором |
| `view_image(file_id, page_or_region)` | Действительно доступное изображение/страница; при отсутствии зрения — явное ограничение |
| `read_log_range(file_id, range)` | Выборка с заголовками, границами и окружающим контекстом |
| `save_report` | Запись результата только в выделенное место, после проверки формы |

Аргументы проверяются как JSON по разрешённой схеме; ID разрешаются только внутри текущей папки. Произвольные команды оболочки и выполнение кода, предложенного моделью, агенту для этой задачи не нужны. Документы остаются данными. Число шагов и размер ответов инструментов ограничиваются настройками запуска; при остановке остаётся частичный результат с перечнем непрочитанного.

Сначала проверяем текст и инструменты. Потом — реальный мультимодальный вход: мелкие надписи, выбранные страницы схем, перекрывающиеся фотографии журнала. Текстовая модель может дать полезный отчёт, но обязана отметить непросмотренные изображения. Для старого DOC нужен проверенный способ чтения; исследовательский разбор основного текста не гарантирует таблицы, вёрстку и встроенные изображения.

Вариант через публичного агента использует ту же папку, инструкцию, словарь и форму результата. Он проверяется отдельно; автоматическую передачу оригиналов во внешний сервис текущий код не делает. Для локального Ollama режим без облачных функций и параметры сервера описаны в [официальном FAQ](https://docs.ollama.com/faq); настройки надо проверять на реально выбранной среде.

## 6. Что будет полезно в отчётах

Сохраняем согласованные 12 разделов. В версии структуры 1.1 уточнены две области, без смены заголовков:

- §9 — одинаковая компактная таблица наличия и форматов, основания связи, чтения содержимого и охвата эпизодов. Полные технические списки остаются в манифесте и §12. В G07 BB найден; это не означает, что его каналы уже прочитаны.
- §10 — поисковые тезисы с категорией, функцией/эпизодом, источником и статусом: например, ложное действие, излишнее действие, отказ, правильная работа, последующая диагностика. Эти тезисы не объявляются метками всех сигналов папки.

Точные объекты и устройства для внутреннего сравнения остаются в §12 с источником. Основной рассказ сохраняет технические роли и относительную хронологию. Словарь подключается отдельным файлом и фиксированной версией. Ни хороший промпт, ни обязательный шаблон не разрешают дописывать недоступные сведения.

Для допуска к массовому проходу нужны: проверяемый состав и след чтения; корректные версии и отрицания; отсутствие выдуманных связей/причин; одинаковая форма отчётов; корректное восстановление после сбоя. Проверка заголовков и JSON будет автоматической, смысловые утверждения пилота — со специалистом. Качество оцениваем по ошибкам и полноте существенного содержания, а не объёму текста.

## 8. Что уточняем по мере выполнения

Перед P6.4 — фактически установленные модели, RAM, рабочий интерфейс сервера и средства чтения. Перед P6.7 — независимые новые папки. Перед P6.8 — расположение полного корпуса, каталог результатов и политика пересмотра принятых отчётов. Проверенный справочник классификационных кодов подключаем только при его наличии; отсутствие справочника не блокирует содержательное чтение документов.
