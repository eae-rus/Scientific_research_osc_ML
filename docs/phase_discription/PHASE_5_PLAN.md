## 1. Ключевая идея Фазы 5

Фаза 4/4.5 доказала рабочий контур:

- спектральное представление из сырых осциллограмм;
- 8-канальный физический контракт;
- SSL pretrain с реконструкцией/прогнозом;
- fine-tuning на ОЗЗ/ДПОЗЗ;
- lazy-загрузчики для тяжёлых CSV;
- ручной запуск через константы в `main` + CLI overrides;
- checkpoint/resume, логи, split-файлы и отчёты.

Фаза 5 должна не переписать это с нуля, а масштабировать:

1. **Старый `data/ml_datasets` не использовать в Phase 5 pretrain.** Он остаётся для фаз 2-4 и regression-проверок.
2. **Основной pretrain делать на реальных неразмеченных данных:**
   - `data/Open_EE_Dataset_v1_3_osc_CSV/` — российская сеть 6-35 кВ, уже первично нормализованная;
   - `data/digital-fault-recording-database/DATA_S.npz` — французские записи RTE, цельные осциллограммы аварий/событий.
3. **Главный task-specific контур Phase 5 — РНМ/PDR.** Аналитические органы сначала реализуются и исследуются отдельно, затем лучший из них используется как teacher для псевдоразметки реальных осциллограмм.
4. **Итоговый PDR не ограничивается имитацией teacher.** После teacher-supervised этапа модель дообучается на сложных случаях с более качественной RTDS и/или ручной COMTRADE-разметкой и сравнивается с исходными аналитическими органами.
5. **ДПОЗЗ/ОЗЗ сохранить как подключаемую задачу.** Simulated_OZZ остаётся размеченным источником гибридного fine-tuning, но его развитие не блокирует основной маршрут Phase 5.
6. **Инфраструктура должна поддерживать новые датасеты и задачи:** не зашивать Open_EE/French и PDR/OZZ как единственные варианты.
7. **Данные читать лениво:** 64 ГБ RAM много, но не достаточно для наивной загрузки всех CSV/NPZ/SimOZZ.

### 1.1. Научная база для корректировки модели

При проектировании Phase 5 использовать документы из `docs/article/` в следующем порядке:

- основной источник по входным признакам: `(ч2.1-англ) Расширенный анализ признаков для ИИ в ЭЭ v1.0.docx`;
- архитектурный контекст: `(ч3) Архитектура трансформеров v1.3.docx`;
- прикладной контекст и ограничения гибридного обучения: `(ч4) Трансформеры для детекции событий v0.3.docx`;
- части 1 и 2 считать историческими источниками, а не актуальным техническим заданием.

Ключевые выводы части 2.1, влияющие на Phase 5:

- выбор признакового пространства оказался важнее выбора архитектуры;
- лучший средний результат дали симметричные составляющие в полярном представлении;
- фазные полярные векторы также сильны и сохраняют индивидуальность фаз, важную для однофазных и направленных задач;
- прямой угол имеет циклический разрыв, поэтому предпочтительно кодирование `(|X|, sin(phi), cos(phi))`;
- мгновенная мощность как самостоятельное входное пространство показала слабый результат, но физические операции мощности/сопротивления могут оставаться внутри PhysicalStem как inductive bias;
- два спектральных снимка «предыстория + текущая точка» почти не уступили полному окну для ряда классификаторов, но последовательные модели извлекали из полного окна дополнительную информацию;
- результат статьи получен на 1600 Гц и другой постановке, поэтому перенос на SSL, разные SPP и PDR должен подтверждаться отдельными абляциями, а не приниматься догматически.

Практическое решение для Phase 5: не перестраивать всю архитектуру до начала основного обучения. Основной Physical KAN-Transformer сохраняется, а модернизация ограничивается входным контрактом, корректной циклической обработкой угла и тремя режимами временного сжатия для PDR: 2 снимка, 5 равномерных снимков и последовательность с шагом 1/8 периода. Низшие гармоники сохраняются, но их число и доля во входе проверяются по размерности/стоимости; сокращение выполняется только при явном разрастании этой ветви.

## 2. Технические инварианты

### 2.1. 8-канальный контракт

Все реальные и симулированные источники должны приводиться к единому виду:

1. `IA`
2. `IB`
3. `IC`
4. `IN`
5. `UA`
6. `UB`
7. `UC`
8. `UN`

Правила:

- если сигнал физически отсутствует, записывать `NaN`, а не `0`;
- `NaN` дальше обрабатывается существующей логикой `DataSanitizer`/missing mask;
- для Open_EE фазные напряжения брать с приоритетом `UA/UB/UC BB`, затем `UA/UB/UC CL`;
- если фазных напряжений нет, но есть линейные `UAB/UBC/UCA`, adapter может временно разместить их в трёх voltage slots только вместе с обязательным `voltage_basis='line'`; feature builder не имеет права трактовать их как `UA/UB/UC`, а рассчитывает допустимые симметричные составляющие по формулам для линейных напряжений и маскирует недоступные фазные признаки (актуально только для случаев с симметричным составляющими, для фазных сигналов - временно класть их в позиции `UA/UB/UC` как `AB/BC/CA` без восстановления фазных, с явным TODO);
- для French: 6 сигналов трактовать как 3 фазных напряжения и 3 фазных тока, `IN` и `UN` заполнять `NaN`;
- исходные датасеты не удалять и не портить, все преобразования писать рядом или в отдельную папку подготовленных данных.

### 2.2. Окна, stride и SPP

`SPP` = samples per period = число отсчётов на один период сети.

Примеры:

- Open_EE `unlabeled_50_1200.csv`: `SPP = 1200 / 50 = 24`;
- Open_EE `unlabeled_50_1600.csv`: `SPP = 32`;
- French `DATA_S.npz`: `SPP = 6400 / 50 = 128`;
- Simulated_OZZ: `SPP` около 769.

Инварианты:

- окно модели = 10 периодов;
- stride по умолчанию = 1/8 периода, потому что это ближе к текущей логике ОЗЗ;
- если `SPP / 8` не целое, сначала использовать `round(SPP / 8)` с логированием фактического шага, затем отдельно исследовать более аккуратные варианты;
- частота сети и частота дискретизации всегда должны быть частью метаданных окна.

### 2.3. Спектральные признаки

Текущий Phase 4 contract содержит 220 каналов:

- 8 сигналов × (9 стандартных + 4 низших) гармоник × `(magnitude, angle)` = 208;
- 6 симметричных составляющих только для первой гармоники × `(magnitude, angle)` = 12.

По результатам части 2.1 этот контракт нельзя автоматически переносить в Phase 5 как окончательный. Требуется `feature_contract_v2`:

1. **Версия A — legacy-совместимая:** фазные/нулевые `phase-polar h1-h9` + симметричные составляющие только h1 (`phase-polar + h1 symmetric`).
2. **Версия B — по результатам части 2.1:** только `symmetric-polar h1-h9`, то есть `I1/I2/I0/U1/U2/U0` для всех доступных стандартных гармоник. Фазные polar-признаки в эту версию не добавляются, чтобы проверить именно самостоятельное представление из статьи.
3. **Циклическая обработка угла:** внешний feature contract сохраняет понятные пары `magnitude + angle`. Внутри PhysicalStem угол используется напрямую только в физически корректных операциях (`torch.polar`, `cos(angle-mta)`), а перед обучаемыми линейными проекциями/attention преобразуется в `sin(angle), cos(angle)` или эквивалентное комплексное представление. Это сохраняет интерпретируемый угол и устраняет разрыв `-pi/pi` там, где он действительно опасен.
4. **Низшие гармоники [2, 4, 6, 10 периодов] сохранить** в обеих версиях в форме, соответствующей основной системе координат конкретной версии. Их состав сокращать только после profiling, без отдельной широкой сетки абляций.
5. **Физические производные не делать обязательным плоским входом:** мощность, сопротивление/проводимость и направленные комбинации предпочтительно вычислять в PhysicalStem из комплексных признаков.
6. **Missing mask вести на уровне физического канала/комплексной компоненты.** Помимо `missing`, хранить происхождение `measured/derived/missing`: аналитически восстановленный канал не равен измеренному, но и не должен полностью маскироваться.
7. **Все преобразования считать on-the-fly** либо из versioned кэша с зафиксированным `feature_contract`.

Правила восстановления и преобразования каналов нужно реализовать отдельно и покрыть тестами:

- восстанавливать ровно одну отсутствующую фазу тока только при наличии достаточного уравнения баланса (и использвать корректного `IN`, если он есть); если отсутствуют две фазы, восстановление неоднозначно и каналы остаются missing;
- поддержать расчёт симметричных составляющих напряжения непосредственно из линейных `UAB/UBC/UCA`, используя существующий/проверенный математический путь, без фиктивной подстановки линейных напряжений в `UA/UB/UC` внутри feature builder;
- не разрешать производным признакам скрывать отсутствие исходных измерений: provenance mask должен доходить до модели;
- точную трактовку `IN/UN`, коэффициентов 3 и знаков для разных источников согласовать с исследователем при реализации adapters.

Для низких частот дискретизации отдельно определить доступные гармоники по Найквисту. Например, при 600/50 Гц `SPP=12`, поэтому нельзя требовать девять гармоник. Недоступная гармоника получает `NaN`/mask и metadata, а число используемых гармоник ограничивается безопасным максимумом ниже/на частоте Найквиста с учётом выбранного FFT. Шаг `SPP/8` округляется детерминированно (`round`, минимум 1), а metadata хранит фактический временной шаг; окно в периодах также переводится в целое число отсчётов единым helper, чтобы исключить рассогласованное округление.

### 2.4. Временной контракт и выход задачи

Нужно разделить три режима, не смешивая их в одном неявном `stride`:

- `sequence_1_8`: спектральные токены по всему 10-периодному окну с шагом 1/8 периода. Это только форма входа; выход может быть позонным, как в ОЗЗ/насыщении ТТ, либо одной меткой последней точки, как в PDR;
- `snapshot_2`: два спектральных снимка из того же окна — первая корректно вычислимая точка/предыстория и последняя точка. Это прежняя сильно сжатая версия, а не отдельный тип разметки;
- `snapshot_5`: пять равномерных снимков по окну, обязательно включая первый допустимый и последний; промежуточные индексы округляются единым детерминированным правилом без повторов;
- `last_state`: Transformer получает историю, но task-head выдаёт одно решение для последней точки или короткой конечной области.

Для PDR основной целевой режим — `last_state`: аналитическая метка относится к текущему моменту, а 10-периодное окно даёт контекст адаптивным органам. Позонный выход можно оставить опциональным для диагностики, но он не должен быть обязательным для PDR.

### 2.5. Совместимость с Phase 4

- старый 220-канальный `mag+angle` контракт обозначить как `feature_contract_v1`;
- новые Phase 5 модели обучать с `feature_contract_v2`;
- checkpoint обязан хранить имя/версию контракта и точный порядок признаков;
- загрузка checkpoint с несовместимым контрактом должна завершаться понятной ошибкой;
- Phase 4 скрипты и тесты не переписывать молча под v2.
- добавить compatibility fixtures: небольшие детерминированные входы и по одному компактному checkpoint каждой поддерживаемой архитектуры/feature contract (если размеры допустимы для Git; иначе скрипт генерации и checksum);
- regression-тест должен загружать legacy checkpoint, выполнять inference и сравнивать shape, отсутствие NaN и контрольный выход с разумным tolerance;
- отдельно проверить миграцию конфигов, `state_dict` и понятную диагностику отсутствующих/лишних ключей.

## 6. Этап 2: формат хранения и индекс осциллограмм

**Цель:** сделать данные быстрыми для случайного чтения и не завязаться на один монолитный формат.

### 6.1. Не конвертировать всё сразу в один большой NPZ

Решение по умолчанию:

- Open_EE оставить исходными CSV как источник истины;
- подготовить шардированное представление для обучения;
- French оставить `DATA_S.npz` как неизменяемый источник истины, но не читать его
  напрямую в случайном training loop из-за deflate-сжатия;
- для French один раз подготовить mmap-доступный NPY либо sharded/chunked
  представление после benchmark и решения о дисковом месте;
- унификацию делать через adapters.

Причина: один гигантский NPZ может стать неудобным для перезаписи, кэширования, частичного пересчёта и восстановления после сбоя. Более практичны shards.

### 6.2. Open_EE shards

Скрипт: `scripts/phase5_experiments/prepare_open_ee_shards.py`

- один файл на одну осциллограмму;
- один shard на 100 осциллограмм;
- один shard на 500/1000 осциллограмм;
- `npz_compressed`;
- обычный `.npy`/`.npz` без сильной компрессии, если чтение окажется важнее размера;
- возможно zarr/parquet только если дадут явное преимущество и не усложнят проект.

Стартовая гипотеза — shards по 100 осциллограмм, но окончательный размер выбирается benchmark из раздела 7.2. Загрузчик извлекает несколько примеров за одно открытие shard, а вероятности групп 1200/1600 Гц и остальных частот считаются по реестру независимо от физической упаковки файлов.

## 7. Этап 3: унифицированный lazy multi-dataset

**Цель:** один PyTorch Dataset для SSL pretrain на нескольких источниках.

Файлы:

- `osc_tools/ml/dataset_registry.py`;
- `osc_tools/ml/phase5_sources.py`;
- `osc_tools/ml/lazy_multi_dataset.py`;
- тесты `tests/unit/test_phase5_dataset_registry.py`;
- тесты `tests/unit/test_phase5_lazy_multi_dataset.py`.

### 7.1. DatasetSource API

Нужен общий интерфейс:

```python
class DatasetSource:
    name: str
    channel_order: tuple[str, ...]

    def __len__(self) -> int: ...
    def get_metadata(self, idx: int) -> dict: ...
    def load_signal(self, idx: int) -> np.ndarray:
        """Return float32 array with shape (8, n_samples). Missing channels are NaN."""
```

Реализации:

- `OpenEEShardedSource`;
- `FrenchRTESource`;
- позже `ComtradeSource`, `SimOZZSource`, другие.

### 7.2. Выборка

Алгоритм `__getitem__` для SSL:

1. выбрать источник по глобальным весам (`open_ee=2/3`, `french=1/3` как стартовая настройка);
2. внутри источника выбрать группу `f_network/f_adc/SPP` пропорционально числу осциллограмм или по пользовательским весам;
3. выбрать осциллограмму;
4. выбрать случайный фрагмент 10 периодов + future-зоны, если они нужны;
5. рассчитать спектр on-the-fly;
6. применить маскирование SSL;
7. вернуть `X`, `target`, `mask`, `metadata`.

Важно: внутри одного batch желательно группировать одинаковый `SPP` или одинаковую итоговую длину спектральной последовательности. Иначе collate будет сложным и может резко увеличить VRAM.

Чтение должно быть shard-aware:

- sampler выбирает источник и группу `f_network/f_adc` по заданным вероятностям, затем shard с поправкой на число доступных записей/окон;
- одно открытие shard используется для извлечения нескольких случайных осциллограмм или окон, а не одного среза;
- порядок этих mini-batches перемешивается, чтобы локальность чтения не превратилась в систематические серии одного режима;
- вероятности считаются по целевым осциллограммам/окнам, а не по числу shards, поэтому размер shard не искажает распределение;
- DataLoader использует настраиваемые `num_workers`, `persistent_workers`, `prefetch_factor`, pinned memory и ограниченный LRU-кэш;
- benchmark сравнивает single-record files и shards на реальном диске по samples/s, RAM, времени первого batch и загрузке GPU/CPU;
- окончательный формат выбирается после benchmark. Shards по 100 записей остаются стартовой гипотезой, а не зафиксированным решением.

### 7.3. Sampling weights

Нужны уровни весов:

- глобально по источникам: например Open_EE 2/3, French 1/3;
- внутри Open_EE по файлам `unlabeled_*`: пропорционально числу осциллограмм, не строк;
- внутри конкретного файла/группы: равномерно по осциллограммам или пропорционально числу доступных окон;
- опционально ограничение `max_windows_per_epoch`, чтобы эпоха не длилась бесконечно (это как раз важный факт, и эпоху предлагаю ограничивать количество примеров).

Стратегии:

- `custom`: пользователь задаёт веса (пока что планируется только на сами датасеты, т.е. речь про Open_EE и French, а на дообучении - ещё ДПОЗЗ и потом насыщение ТТ - этот датасет появится позже);
- `proportional_records`: по числу осциллограмм;
- `proportional_windows`: по числу окон;
- `balanced_sources`: одинаковый вес источников;
- `debug_small`: фиксированный малый поднабор.

### 7.4. Кэширование

Минимум:

- LRU-кэш на загруженные осциллограммы;
- ограничение по числу записей и по памяти;
- отключаемый кэш для тестов;
- логирование hit/miss на debug.

## 8. Этап 4: модернизация признаков и Physical KAN-Transformer

**Цель:** реализовать выводы части 2.1 до масштабного SSL, сохранив воспроизводимый legacy baseline.

### 8.1. Feature builder v2

Нужно выделить расчёт признаков из `compute_spectral_from_raw` в конфигурируемый builder, например:

- `osc_tools/ml/spectral_features.py`;
- `SpectralFeatureConfig`;
- `SpectralFeatureBuilder`;
- сериализуемый `FeatureSchema` с именами, группами, порядком и masks.

Builder должен поддерживать:

- `phase_polar`: h1-h9 и опциональные low harmonics;
- `symmetric_polar`: h1-h9 для токов и напряжений;
- внешний формат `angle_encoding='angle'` как Phase 5 default, с циклическим encoding внутри модели перед непериодическими обучаемыми операциями;
- отключение отдельных ветвей для диагностики и будущих абляций;
- одинаковый результат для разных `SPP` при одинаковом физическом сигнале в пределах численной погрешности;
- корректную обработку отсутствующих фаз/нулевых каналов;
- metadata о реально доступных гармониках.

Минимальные тесты:

- аналитические трёхфазные синусоиды прямой/обратной/нулевой последовательности;
- правило порядка последовательности для h1-h9;
- эквивалентность физических операций для углов около `-pi/pi` и непрерывность внутреннего `sin/cos` encoding;
- NaN propagation и masks;
- одинаковая физическая фаза при 50 и 60 Гц;
- недоступные гармоники при малом SPP.

### 8.2. Ограниченная модернизация PhysicalStem

Проверка текущего кода показывает смешанную картину:

- `torch.polar(amplitude, angle)` и `DirectionalRelayGate` через `cos(angle-mta)` циклически корректны;
- обучаемая проекция `proj_angle` и raw-angle dot product в `ComplexMultiheadAttention` не являются циклически инвариантными около `-pi/pi`.

Поэтому Phase 5 не требует новой архитектуры с нуля. Нужно сохранить пары `(magnitude, angle)` и текущие физические блоки, но:

1. перед `proj_angle` и фазовыми Q/K/V преобразовать углы в `sin/cos` или циклический embedding;
2. оставить исходный угол для `torch.polar`, MTA и объяснимого debug output;
3. обеспечить маскирование до циклического encoding;
4. поддержать оба самостоятельных feature schema без fusion фазной и полной symmetric-polar версий;
5. проверить определение комплексной мощности/сопротивления и необходимость сопряжения;
6. сохранить runtime/конфигурационный fallback к legacy stem.

### 8.3. Минимальный выбор конфигурации

Из-за ограниченных вычислительных ресурсов не проводить полную факторную сетку. Реализовать две версии одной архитектуры:

1. **Version A:** текущий `phase-polar + h1 symmetric` с низшими гармониками;
2. **Version B:** самостоятельный `symmetric-polar h1-h9` по части 2.1, также с низшими гармониками, без добавления фазных polar-признаков.

Циклический encoding угла считать инженерной корректировкой обеих версий, а не третьей исследуемой моделью; legacy raw-angle путь сохраняется только для совместимости и regression-проверок.

Псевдоразметка PDR строится из h1 symmetric, поэтому сравнение на способности копировать teacher потенциально благоприятствует Version B или признакам, напрямую совпадающим с teacher. Выбор между A/B нельзя делать только по pseudo-label accuracy: учитывать SSL validation, независимые сложные/ручные данные, устойчивость, вычислительную стоимость и итоговую переносимость.

Три режима PDR (`snapshot_2`, `snapshot_5`, `sequence_1_8`) сравниваются позднее на уже выбранной модели и не требуют трёх разных архитектур. Низшие гармоники сначала оставить `[2, 4, 6, 10]`; если profiling покажет чрезмерную долю каналов/времени, проверить один сокращённый вариант, например `[2, 4, 10]`, без широкого перебора.

Решение принимается по стабильности, SSL validation, памяти/скорости и малому PDR probe. Полную оценку feature/architecture combinations оставить как дальнейшее совместное исследование с внешними центрами.

Выход этапа:

- зафиксированный `feature_contract_v2`;
- выбранная конфигурация Physical KAN-Transformer;
- legacy v1 остаётся запускаемым;
- отчёт `reports/phase5/feature_architecture_ablation.md`.

## 9. Этап 5: Phase 5 SSL pretrain

**Цель:** обучать модель без учителя на реальных данных.

В SSL полезны все типы пригодных процессов Open_EE и French/RTE: аварийные и
неаварийные записи не исключаются по метке. Однако нужны два явно разных протокола:

- `research_strict`: до pretrain фиксируется file-level never-seen holdout по
  каждому источнику; эти осциллограммы не участвуют ни в SSL, ни в подборе
  feature/scheduler и используются для честного downstream/transfer вывода;
- `full_archive`: после завершения сравнительного исследования финальный рабочий
  backbone можно дообучить на всём архиве, включая holdout, но его метрики уже
  нельзя выдавать за независимую оценку переноса.

Если первый масштабный прогон запускается без strict holdout, он маркируется как
transductive/exploratory. Само отсутствие task labels в SSL не устраняет overlap
по осциллограммам и близким физическим режимам.

Новый скрипт:

- `scripts/phase5_experiments/run_phase5_pretrain.py`

Он должен наследовать стиль Phase 4:

- ручной блок констант внизу файла;
- CLI overrides;
- `--smoke`;
- `--resume`;
- `--reset-optimizer`;
- `latest_checkpoint.pt`;
- `best_model.pt`;
- `config.json`;
- `training_log.jsonl`;
- экспорт кривых.

### 9.1. Pretext tasks

Базовый набор:

- masked spectral-temporal modeling: скрываем часть временных зон/физических групп и восстанавливаем спектральные признаки;
- реконструкция признаков выбранной Version A/B с метриками по физическим группам;
- прогноз будущих зон, если текущая архитектура стабильно это держит;
- опциональная consistency между фазным и симметричным представлением одного
  сигнала — только после устойчивого базового masked-reconstruction и без
  обязательного объединения Version A/B в одну архитектуру;
- опционально contrastive/consistency-задача между разными augmentations одной осциллограммы, но только после базовой стабильности.

Не надо сразу превращать Phase 5 в архитектурный зоопарк. Первое качество фазы — надёжная инфраструктура и воспроизводимое обучение.

### 9.2. Loss

База:

- оставить `SpectralReconstructionLoss`/`ComplexMSELoss` как старт;
- проверить работу при `NaN` каналах;
- логировать компоненты loss отдельно: current, future, masked, per-channel group.

Исследовать улучшения:

- Huber/SmoothL1 поверх комплексной ошибки для устойчивости к выбросам;
- амплитудно-фазовый loss с раздельными весами;
- относительная ошибка с нижним порогом шума, как в Phase 4;
- channel-balanced loss, чтобы отсутствующие/малые каналы не ломали масштаб;
- curriculum: сначала h1 и базовые гармоники, затем расширенный спектр.

### 9.3. LR scheduler

Проблема не в “косинусной функции потерь”, а в управлении скоростью обучения. В Phase 5 нужен выбор scheduler, который реагирует на процесс.

Поддержать:

- `cosine_warmup` как legacy baseline;
- `cosine_warm_restarts`;
- `reduce_on_plateau` по `val_loss`;
- `onecycle` для коротких прогонов;
- `warmup_plateau_decay`: warmup -> plateau monitoring -> decay;
- логирование фактического LR каждую эпоху.

Стартовая рекомендация:

- для длинного SSL: warmup + `ReduceLROnPlateau` или warmup + cosine restarts;
- для коротких smoke/ablation: `OneCycleLR`;
- early stopping по умолчанию выключить, потому что запуск ручной и долгий, но предупреждения о стагнации логировать.

### 9.4. Validation

Validation-набор должен быть стабильным:

- фиксированный seed;
- зафиксированный до обучения file-level split, его hash и список осциллограмм;
- окна validation детерминированы либо генерируются фиксированным manifest;
- отдельно Open_EE-val и French-val;
- общая val-метрика и per-source метрики;
- отдельно различать SSL validation (подбор обучения) и never-seen downstream holdout;
- сохранять несколько реконструкций в отчёт/PNG для визуального контроля;
- небольшой frozen-backbone PDR linear probe после контрольных checkpoint, чтобы SSL не оптимизировался только под удобную реконструкцию.

## 11. Этап 7: РНМ/PDR как основная прикладная демонстрация

**Цель:** построить и исследовать интеллектуальный направленный измерительный орган, использующий 200 мс предыстории, но принимающий решение для текущего момента.

### 11.1. Формализация аналитических органов

Математика будет добавлена исследователем позднее; до этого не придумывать формулы и уставки самостоятельно. Публичные и закрытые органы разделить архитектурно.

Публичная часть репозитория:

- `docs/phase_discription/PHASE_5_PDR_ALGORITHMS.md` содержит открытые алгоритмы, общий интерфейс и анонимизированный перечень закрытых вариантов без раскрытия формул;
- `osc_tools/pdr/` содержит `PDRAlgorithm`, registry, открытые реализации и fallback policy;
- конфигурация выбирает орган по стабильному ID, а не импортирует закрытую функцию напрямую;
- если выбранный закрытый орган недоступен, программа выдаёт явное предупреждение, записывает факт fallback в config/log и выбирает заданный исследователем открытый fallback. Нельзя незаметно подменять teacher.

Закрытая часть:

- отдельная локальная папка, например `private/pdr_algorithms/`, целиком исключённая через `.gitignore` и отсутствующая в публичных fixtures, логах и отчётах;
- приватный registry подключается опционально и реализует тот же интерфейс;
- документация/результаты используют анонимные ID и агрегированные метрики;
- тесты закрытых функций хранятся рядом в приватной папке и не раскрывают формулы через ожидаемые промежуточные значения;
- перед публикацией добавить автоматическую проверку `git ls-files`/поиск запрещённых путей и секретных ID.

Текстовый комментарий «не копировать» не обеспечивает защиту коммерческой тайны. Реальная защита требует файловых прав, приватного репозитория/зашифрованного хранилища и, если потребуется передача исполняемого кода без исходников, отдельного скомпилированного пакета или сервиса. До выбора схемы распространения закрытые исходники не должны попадать в контекст публичных агентов и автоматические отчёты.

Для каждого доступного органа предварительно фиксировать (состав полей скорректировать после получения первых алгоритмов):

- идентификатор и версию алгоритма;
- используемые величины: фазные или прямой последовательности h1;
- источник поляризующего напряжения/тока;
- текущие величины и величины `t-200 ms`, если орган адаптивный;
- угол максимальной чувствительности и зона действия;
- амплитудные уставки, блокировки, выдержки и hysteresis;
- требования к наличию каналов;
- единицы, нормировку и направление знаков;
- форму выхода: binary start/trip, continuous margin, angle margin, confidence;
- поведение при NaN и недостаточной предыстории.

Реализация:

- общий интерфейс `PDRAlgorithm`;
- чистые векторизованные функции без зависимости от PyTorch Dataset;
- конфигурации органов отдельно от кода;
- unit-тесты открытых органов на аналитических фазорах и граничных углах;
- приватные тесты закрытых органов без публикации формул и чувствительных эталонных трасс;
- trace/debug output, объясняющий причину действия органа.

### 11.2. Статистическое исследование органов

Конкретный протокол статистики определить после получения математики, но инфраструктура должна уметь считать:

- долю срабатываний по источникам/объектам/режимам;
- распределения рабочих величин и margins;
- согласие между органами;
- случаи, где органы расходятся;
- устойчивость только к тем уставкам, которые для конкретной версии объявлены практически регулируемыми; registry хранит `tunable_parameters`, допустимые диапазоны и fixed-параметры;
- стабильность решения/chattering; время первого действия оставить опциональной инженерной метрикой, не обязательной для первичного выбора PDR;
- зависимость от отсутствующих каналов и качества напряжения;
- отдельные статистики по Open_EE и French, учитывая разные классы напряжения и нормировку.

Статистика на неразмеченных данных нужна для понимания поведения и поиска аномалий, но не определяет объективно лучший орган. Teacher для псевдоразметки выбирает исследователь по личному опыту и инженерным основаниям. Сравнение качества органов откладывается до появления эталонных RTDS/ручных данных.

### 11.3. Псевдоразметка реальных данных лучшим органом

После решения исследователя о teacher-алгоритме:

1. прогнать его по пригодным Open_EE и, если физически сопоставимо, French-записям;
2. прогонять плавающее 10-периодное окно: каждая допустимая конечная точка получает teacher-метку, поэтому итоговая разметка почти поточечная; первые 10 периодов имеют `unknown/warmup`;
3. дополнительно сохранять непрерывные диагностические величины и confidence/margin;
4. сохранять `teacher_id`, версию, конфиг и hash входной осциллограммы;
5. не смешивать train/val окна одной осциллограммы;
6. на первом этапе делать split по целым осциллограммам со стратификацией/контролем по исходному датасету; объектный split добавить позже, когда появятся надёжные object IDs.

Эта разметка является **weak/pseudo-label**, а не независимой истиной. Поэтому нужны:

- базовый этап использует полные teacher-метки и warmup mask;
- confidence filtering, soft targets/sample weights и игнорирование пограничных точек оставить как последующее улучшение после появления подходящего margin у выбранного органа;
- отдельный набор расхождений нескольких органов для последующего исследования;
- frozen teacher benchmark: нейросеть должна сравниваться с органом, который создал метки.

### 11.4. Первое PDR fine-tuning

Основная постановка:

- вход: последовательность спектральных токенов за 10 периодов;
- выход: решение в последней точке (`last_state`), опционально короткая конечная область;
- входной минимум для classical PDR probe: h1 прямой последовательности U/I либо фазные h1;
- полный Physical KAN получает также остальные гармоники и low-frequency context, чтобы исследовать полезность дополнительной информации;
- сравнить random init, frozen SSL backbone, частично размороженный и полный fine-tuning;
- сравнить три формы одного входного окна: `snapshot_2`, `snapshot_5` и, если обучение по ресурсам допустимо, `sequence_1_8`;
- исследовать auxiliary regression по margin/рабочей величине, а не только бинарную BCE.

### 11.5. Пост-обучение на сложных случаях

После обучения на псевдоразметке собрать отдельный high-quality dataset:

- сложные случаи, сгенерированные в RTDS;
- вручную доразмеченные COMTRADE;
- случаи расхождения аналитических органов;
- ложные/пограничные срабатывания teacher;
- режимы с пропавшими каналами, насыщением ТТ, помехами и коммутациями.

Форму разметки определить совместно с исследователем. Предпочтительно хранить не только класс, но и:

- направление;
- факт пуска/блокировки;
- доверие эксперта;
- интервал неопределённости;
- тип сложного режима;
- при наличии — непрерывную целевую рабочую величину.

Базовая стратегия пост-обучения: обычный fine-tuning на объединении pseudo-label данных и нового качественно размеченного набора, с настраиваемым весом источников. Отдельная градация сложности не обязательна. Сохранить контрольный replay-поднабор обычных режимов для проверки забывания; curriculum, distillation и сложные схемы добавлять только при обнаруженной проблеме, а не заранее.

### 11.6. Итоговое сравнение PDR

Сравнить:

- все реализованные аналитические органы;
- teacher-орган;
- модель после pseudo-label fine-tuning;
- модель после post-training;
- random-init neural baseline;
- компактный baseline на `U1/I1 h1` и `snapshot_2`;
- компактную/прореженную версию выбранного Physical KAN (`snapshot_5` или `sequence_1_8`) для оценки реализуемости на существующих устройствах РЗА.

Метрики окончательно определить после постановки органов, но предусмотреть sensitivity/selectivity, false operation rate, delay, stability/chattering, calibration, сложность и CPU latency.

**Исследовательская заметка после основного сравнения:** оценить регулируемость нейросетевого PDR. Полностью фиксированный орган трудно адаптировать к нестандартному объекту. Возможные направления — явные пользовательские входы/условия (порог чувствительности по ТТ, разрешение отдельных функций), несколько калибруемых режимов или вынесенный порог поверх непрерывного score. Это не является обязательной частью первого исследования и проектируется только после анализа итоговой модели, чтобы не создать фиктивные «уставки», не имеющие физического смысла.

## 15. Предлагаемая последовательность реализации

1. **Phase 4 safety pass — основной набор выполнен**
   - Transformer/augmentation/CT saturation и новые контракты проверены;

   - выполнить полный Open_EE scan подготовленным потоковым скриптом;

   - сформировать отчёт по нормировке French после RMS;
   - исключения real_OZZ из Open_EE.

3. **Small prototype**
   - сделать Open_EE shards на малом поднаборе;
   - сделать French adapter;
   - проверить 8-канальный контракт;
   - проверить `compute_spectral_from_raw` на Open_EE и French.

   - общий индекс;
   - weighted sampling;
   - batch grouping по SPP;
   - тесты.

   - 1-2 источника;
   - маленький `max_windows_per_epoch`;
   - проверка resume;
   - визуализация реконструкции.

   - стартовые веса Open_EE/French = 2/3 и 1/3;

   - исследователь выбирает teacher по инженерному опыту с учётом собранной статистики.

9. **Pseudo-label PDR fine-tuning**
   - разметить реальные данные teacher-органом;
   - сравнить last-state sequence и snapshot baselines;
   - сохранить confidence/margins.

10. **PDR post-training**
   - RTDS и/или ручная COMTRADE-разметка сложных случаев;
   - итоговое сравнение аналитических и нейросетевых органов.

11. **Подключаемые OZZ и другие задачи**
   - только когда они снова станут активной исследовательской целью.

## 17. Главные риски

1. **Open_EE уже нормализован.** Повторная нормировка через `norm_coef_all_v1.4.csv` испортит масштаб.
2. **French current nominal неизвестен.** Нельзя молча выбрать делитель по максимуму КЗ. Сначала RMS/квантили, затем ручное решение.
3. **Разные SPP.** Нужно batch grouping или padding/mask, иначе обучение станет нестабильным и тяжёлым по VRAM.
4. **Огромные CSV.** Нельзя использовать pandas/polars так, чтобы файл целиком попадал в RAM.
5. **Слишком ранняя конвертация всего архива.** Сначала прототип shards и benchmark чтения.
6. **Смешение pretrain и fine-tuning источников.** SimOZZ не должен незаметно попасть в SSL как “реальные данные”.
7. **Неправильный real_no_OZZ.** Из Open_EE надо исключить известные ОЗЗ по отчёту, иначе normal-класс будет загрязнён.
8. **Слом Phase 4.** Все новые адаптеры должны добавляться рядом, без разрушения текущих скриптов.
9. **Сырой угол в обучаемых проекциях.** Внешний `magnitude+angle` сохраняется, но linear/attention пути должны получать циклический encoding около `-pi/pi`.
10. **Слепое следование части 2.1.** Статья исследовала supervised-классификацию при 1600 Гц, а Phase 5 включает SSL, PDR и разные SPP; новый контракт нужно подтвердить абляциями.
11. **Teacher leakage.** Оценка PDR на псевдоразметке того же аналитического органа измеряет прежде всего способность копировать teacher, а не улучшение защиты.
12. **Наследование ошибок teacher.** На первом этапе используются полные teacher-метки; margin/confidence нужно сохранять, чтобы позднее добавить фильтрацию и переоценить пограничные решения.
13. **Domain shift PDR.** French — сеть другого класса напряжения и типа заземления; применение одних PDR-формул/уставок требует физического обоснования.
14. **Утечка между окнами.** Первый split делается по целым осциллограммам и контролируется по источнику, а не по случайным окнам; объектный split станет возможен после появления object IDs.
15. **Catastrophic forgetting при post-training.** Сложные случаи не должны уничтожить поведение на обычных режимах; нужен replay/смешанный контроль.
16. **Утечка коммерческой тайны.** `.gitignore` снижает риск случайного commit, но не заменяет права доступа и приватное хранение; закрытые алгоритмы нельзя включать в публичные логи, fixtures и контексты автоматических агентов.
17. **Transductive overlap.** Если downstream test-осциллограммы участвовали в
SSL без меток, это не label leakage в узком смысле, но независимость transfer
оценки нарушена. Такие прогоны маркируются exploratory; для научного вывода нужен
never-seen file-level holdout, зафиксированный до pretrain.

## 18. Стартовые решения по умолчанию

- Open_EE/French weights для первого полного pretrain: `0.667 / 0.333`.
- Первый сравнительный SSL-протокол: `research_strict`; `full_archive` допустим
  после выбора конфигурации для финального рабочего backbone.
- Окно: 10 периодов.
- Stride: 1/8 периода.
- Open_EE storage: benchmark single-record и shard layouts; 100 записей на shard — стартовая гипотеза.
- French storage: оставить `DATA_S.npz` источником истины; training adapter
  использует только отдельно подготовленный random-access NPY/shards после benchmark.
- French voltage normalization: `value * 18.310 / (90000 * 3)` (проверить).
- French current normalization: после RMS-отчёта, параметр задаётся явно.
- Missing channels: `NaN`.
- Phase 5 features: две schema внутри `feature_contract_v2` — A (`phase-polar + h1 symmetric`) и B (`symmetric-polar h1-h9` без фазной ветви), обе с low harmonics; внешний формат `magnitude+angle`, внутренние непериодические проекции получают циклический encoding.
- Legacy Phase 4 features: `feature_contract_v1`, только для совместимости и baseline.
- PDR output: `last_state` по последней точке 10-периодного окна; сравниваются `snapshot_2`, `snapshot_5` и при доступных ресурсах `sequence_1_8`.
- PDR pseudo-labels: хранить teacher version, margin/confidence и маску неопределённых случаев.
- OZZ: task adapter сохраняется, но не блокирует путь data -> feature v2 -> SSL -> PDR.
- Scheduler для первого длинного SSL: warmup + `ReduceLROnPlateau` или warmup + cosine restarts; выбор зафиксировать после smoke.
- Early stopping: выключен, но логировать стагнацию.
- Main style: ручные константы + CLI как в Phase 4.
