# План Фазы 5: предобучение на реальных осциллограммах и дообучение под задачи

-> **Статус:** план к реализации  
**Цель:** продолжить Фазу 4/4.5, модернизировать признаковое пространство Physical KAN-Transformer по результатам нового исследования и предобучить общий backbone на большом наборе реальных осциллограмм. Главной прикладной демонстрацией Фазы 5 становится интеллектуальный орган направления мощности (РНМ/PDR): сначала воспроизведение и сравнение аналитических органов, затем обучение по их псевдоразметке реальных данных и пост-обучение на сложных размеченных случаях. ДПОЗЗ/ОЗЗ остаётся подключаемой демонстрационной задачей, но не входит в первую очередь работ.

---

## 1. Ключевая идея Фазы 5

Фаза 4/4.5 доказала рабочий контур:

- спектральное представление из сырых осциллограмм;
- 8-канальный физический контракт;
- SSL pretrain с реконструкцией/прогнозом;
- fine-tuning на ОЗЗ/ДПОЗЗ;
- lazy-загрузчики для тяжёлых CSV;
- ручной запуск через константы в `main` + CLI overrides;
- checkpoint/resume, логи, split-файлы и отчёты.

Фаза 5 должна не переписать это с нуля, а масштабировать:

1. **Старый `data/ml_datasets` не использовать в Phase 5 pretrain.** Он остаётся для фаз 2-4 и regression-проверок.
2. **Основной pretrain делать на реальных неразмеченных данных:**
   - `data/Open_EE_Dataset_v1_3_osc_CSV/` — российская сеть 6-35 кВ, уже первично нормализованная;
   - `data/digital-fault-recording-database/DATA_S.npz` — французские записи RTE, цельные осциллограммы аварий/событий.
3. **Главный task-specific контур Phase 5 — РНМ/PDR.** Аналитические органы сначала реализуются и исследуются отдельно, затем лучший из них используется как teacher для псевдоразметки реальных осциллограмм.
4. **Итоговый PDR не ограничивается имитацией teacher.** После teacher-supervised этапа модель дообучается на сложных случаях с более качественной RTDS и/или ручной COMTRADE-разметкой и сравнивается с исходными аналитическими органами.
5. **ДПОЗЗ/ОЗЗ сохранить как подключаемую задачу.** Simulated_OZZ остаётся размеченным источником гибридного fine-tuning, но его развитие не блокирует основной маршрут Phase 5.
6. **Инфраструктура должна поддерживать новые датасеты и задачи:** не зашивать Open_EE/French и PDR/OZZ как единственные варианты.
7. **Данные читать лениво:** 64 ГБ RAM много, но не достаточно для наивной загрузки всех CSV/NPZ/SimOZZ.

Ключевые выводы части 2.1, влияющие на Phase 5:

- выбор признакового пространства оказался важнее выбора архитектуры;
- лучший средний результат дали симметричные составляющие в полярном представлении;
- фазные полярные векторы также сильны и сохраняют индивидуальность фаз, важную для однофазных и направленных задач;

- результат статьи получен на 1600 Гц и другой постановке, поэтому перенос на SSL, разные SPP и PDR должен подтверждаться отдельными абляциями, а не приниматься догматически.

Есть мысли, что несколько промежуточных точек всё же могут быть полезны. А также, можно бы оставить низшие гармоники (но подумать, не составляют ли они большую долю? Тогда взять меньше низших гармоник).

## 2. Технические инварианты

### 2.1. 8-канальный контракт

Все реальные и симулированные источники должны приводиться к единому виду:

1. `IA`
2. `IB`
3. `IC`
4. `IN`
5. `UA`
6. `UB`
7. `UC`
8. `UN`

Правила:

- если сигнал физически отсутствует, записывать `NaN`, а не `0`;
- `NaN` дальше обрабатывается существующей логикой `DataSanitizer`/missing mask;
- для Open_EE фазные напряжения брать с приоритетом `UA/UB/UC BB`, затем `UA/UB/UC CL`;
- если фазных напряжений нет, но есть линейные `UAB/UBC/UCA`, временно класть их в позиции `UA/UB/UC` как `AB/BC/CA` без восстановления фазных, с явным TODO;
- для French: 6 сигналов трактовать как 3 фазных напряжения и 3 фазных тока, `IN` и `UN` заполнять `NaN`;
- исходные датасеты не удалять и не портить, все преобразования писать рядом или в отдельную папку подготовленных данных.

### 2.2. Окна, stride и SPP

`SPP` = samples per period = число отсчётов на один период сети.

Примеры:

- Open_EE `unlabeled_50_1200.csv`: `SPP = 1200 / 50 = 24`;
- Open_EE `unlabeled_50_1600.csv`: `SPP = 32`;
- French `DATA_S.npz`: `SPP = 6400 / 50 = 128`;
- Simulated_OZZ: `SPP` около 769.

Инварианты:

- окно модели = 10 периодов;
- stride по умолчанию = 1/8 периода, потому что это ближе к текущей логике ОЗЗ;
- если `SPP / 8` не целое, сначала использовать `round(SPP / 8)` с логированием фактического шага, затем отдельно исследовать более аккуратные варианты;
- частота сети и частота дискретизации всегда должны быть частью метаданных окна.

### 2.3. Спектральные признаки

Текущий Phase 4 contract содержит 220 каналов:

- 8 сигналов × (9 стандартных + 4 низших) гармоник × `(magnitude, angle)` = 208;
- 6 симметричных составляющих только для первой гармоники × `(magnitude, angle)` = 12.

По результатам части 2.1 этот контракт нельзя автоматически переносить в Phase 5 как окончательный. Требуется `feature_contract_v2`:

1. **Основная ветвь symmetric-polar:** `I1/I2/I0/U1/U2/U0` для всех доступных стандартных гармоник, а не только h1.
2. **Параллельная phase-polar ветвь:** фазные и нулевые каналы сохраняются, поскольку симметричные составляющие могут скрывать индивидуальность повреждённой фазы.
3. **Циклическое кодирование:** каждая комплексная компонента представляется как `magnitude + sin(angle) + cos(angle)` либо эквивалентной непрерывной комплексной парой. Сырой угол не должен проходить через обычные линейные операции как евклидова координата.
4. **Низшие гармоники [2, 4, 6, 10 периодов] сохранить**, но оформить как отдельную медленную/context ветвь. Для них нужны абляции `без low / low только symmetric / low phase+symmetric`, а не безусловное дублирование полного набора.
5. **Физические производные не делать обязательным плоским входом:** мощность, сопротивление/проводимость и направленные комбинации предпочтительно вычислять в PhysicalStem из комплексных признаков.
6. **Missing mask вести на уровне физического канала/комплексной компоненты**, чтобы отсутствующий сигнал не превращался в валидные `sin(0), cos(0)`. (Примечание автора: Хмм... Надо проверить корректность обработок случаев с отсутствием сигналов, чтобы если нет 2 сигналов, то третий считался из фазных и N, если он есть, так же стоит заложить расчёт последовательностей из линейных напряжений, ибо иногда присутствуют они, а не фазные. И вообще обдумать маскирование в этом случае, чтобы не вызывало сильных проблем, например из-за маскирования фаз А и С. В общем не забыть получше обдумать, и если надо, то спросить моё мнение)
7. **Все преобразования считать on-the-fly** либо из versioned кэша с зафиксированным `feature_contract`.

Для низких частот дискретизации отдельно определить доступные гармоники по Найквисту. Недоступная гармоника должна иметь `NaN`/mask и metadata, а не нулевое значение, неотличимое от физического нуля. (примечание автора: Надо предусмотреть защиту и для высших, и возможно заложить округление при щагах сетки / окна в случае, если исходный размер не кратен 8. Т.к. есть осциллограммы и с частотой 600Гц на сетевую - 50Гц, т.е. всего 12 точек и 6 гармоник.)

### 2.4. Временной контракт и выход задачи

Нужно разделить три режима, не смешивая их в одном неявном `stride`:

- `sequence`: несколько спектральных токенов за 10 периодов — основной режим SSL и задач, где важна динамика (примечание автора: Если верно понял - то это разметка указанной последовательности, как в задаче с ОЗЗ и насыщения ТТ в конце фазы 4);
- `snapshot_pair`: предыстория около `t-200 ms` и последняя доступная точка — сильный компактный baseline из части 2.1 (Примечание автора: Если честно, не понял этот вариант);
- `last_state`: Transformer получает историю, но task-head выдаёт одно решение для последней точки или короткой конечной области.

Для PDR основной целевой режим — `last_state`: аналитическая метка относится к текущему моменту, а 10-периодное окно даёт контекст адаптивным органам. Позонный выход можно оставить опциональным для диагностики, но он не должен быть обязательным для PDR.

### 2.5. Совместимость с Phase 4

- старый 220-канальный `mag+angle` контракт обозначить как `feature_contract_v1`;
- новые Phase 5 модели обучать с `feature_contract_v2`;
- checkpoint обязан хранить имя/версию контракта и точный порядок признаков;
- загрузка checkpoint с несовместимым контрактом должна завершаться понятной ошибкой;
- Phase 4 скрипты и тесты не переписывать молча под v2.

(Примечание автора: Главное сперва защитить тестами чего не хватает / если не хватает, чтобы модели старые точно запускались, можно прям файлы специальные с моделями сохранить даже. Может и сейчас нормально, но лучше проверить, так как были сложности несколько раз.)

## 6. Этап 2: формат хранения и индекс осциллограмм

**Цель:** сделать данные быстрыми для случайного чтения и не завязаться на один монолитный формат.

### 6.1. Не конвертировать всё сразу в один большой NPZ

Решение по умолчанию:

- Open_EE оставить исходными CSV как источник истины;
- подготовить шардированное представление для обучения;
- French оставить `DATA_S.npz` как источник истины;
- унификацию делать через adapters.

Причина: один гигантский NPZ может стать неудобным для перезаписи, кэширования, частичного пересчёта и восстановления после сбоя. Более практичны shards.

### 6.2. Open_EE shards

Скрипт: `scripts/phase5_experiments/prepare_open_ee_shards.py`

Варианты, которые нужно протестировать на малом поднаборе:

- один файл на одну осциллограмму;
- один shard на 100 осциллограмм;
- один shard на 500/1000 осциллограмм;
- `npz_compressed`;
- обычный `.npy`/`.npz` без сильной компрессии, если чтение окажется важнее размера;
- возможно zarr/parquet только если дадут явное преимущество и не усложнят проект.

Предпочтение на старте: shards по 100 осциллограмм. Это компромисс между миллионами мелких файлов и огромными монолитами. Но стоит корректно учесть это в файлах подгрузки рандомных примеров, чтобы не осуществлялась загрузка этого shard-а ради одного примера, и так кучу файлов открывать. Стоит сделать загрузку по несколько файлов из данного shard, но учесть частотность по примера (чтобы чаще брались из 1200Гц и 1600Гц примеры). В общем обдумать глубоко, как лучше бы сделать равновероятное взятие примеров по их частотности.

Каждый shard должен хранить:

- `signals`: массивы 8 каналов, по возможности `float32`;
- `file_names`;
- `lengths`;
- `f_network`;
- `f_adc`;
- `spp`;
- `channel_order`;
- `source_csv`;
- `normalized=true`;
- `normalization_note="Open_EE already divided by CT/PT nominal values and reserve factors"`.

Если длины осциллограмм разные, не паддить всё до максимума без необходимости. Лучше хранить список массивов или плоский массив + offsets.

## 7. Этап 3: унифицированный lazy multi-dataset

**Цель:** один PyTorch Dataset для SSL pretrain на нескольких источниках.

Файлы:

- `osc_tools/ml/dataset_registry.py`;
- `osc_tools/ml/phase5_sources.py`;
- `osc_tools/ml/lazy_multi_dataset.py`;
- тесты `tests/unit/test_phase5_dataset_registry.py`;
- тесты `tests/unit/test_phase5_lazy_multi_dataset.py`.

### 7.1. DatasetSource API

Нужен общий интерфейс:

```python
class DatasetSource:
    name: str
    channel_order: tuple[str, ...]

    def __len__(self) -> int: ...
    def get_metadata(self, idx: int) -> dict: ...
    def load_signal(self, idx: int) -> np.ndarray:
        """Return float32 array with shape (8, n_samples). Missing channels are NaN."""
```

Реализации:

- `OpenEEShardedSource`;
- `FrenchRTESource`;
- позже `ComtradeSource`, `SimOZZSource`, другие.

### 7.2. Выборка

Алгоритм `__getitem__` для SSL:

1. выбрать источник по глобальным весам (`open_ee=2/3`, `french=1/3` как стартовая настройка);
2. внутри источника выбрать группу `f_network/f_adc/SPP` пропорционально числу осциллограмм или по пользовательским весам;
3. выбрать осциллограмму;
4. выбрать случайный фрагмент 10 периодов + future-зоны, если они нужны;
5. рассчитать спектр on-the-fly;
6. применить маскирование SSL;
7. вернуть `X`, `target`, `mask`, `metadata`.

Важно: внутри одного batch желательно группировать одинаковый `SPP` или одинаковую итоговую длину спектральной последовательности. Иначе collate будет сложным и может резко увеличить VRAM. 

**Примечание:** И ещё комментарий: обработку стоит обдумать так, чтобы не открывать shard-ы ради одного "среза", ибо загрузка данных файлов может быть узким горлышком. Вероятно лучше будет сделать по 1 файлы хранение файлов, или обработку сразу нескольких разных примеров. Плюс надо бы задать параллельную обработку с обучением, чтобы не тормозить процессы по возможности. В общем, нужно будет обдумать этот момент для осмысления ускорения обработку без порчи случайно выборки.

### 7.3. Sampling weights

Нужны уровни весов:

- глобально по источникам: например Open_EE 2/3, French 1/3;
- внутри Open_EE по файлам `unlabeled_*`: пропорционально числу осциллограмм, не строк;
- внутри конкретного файла/группы: равномерно по осциллограммам или пропорционально числу доступных окон;
- опционально ограничение `max_windows_per_epoch`, чтобы эпоха не длилась бесконечно (это как раз важный факт, и эпоху предлагаю ограничивать количество примеров).

Стратегии:

- `custom`: пользователь задаёт веса (пока что планируется только на сами датасеты, т.е. речь про Open_EE и French, а на дообучении - ещё ДПОЗЗ и потом насыщение ТТ - этот датасет появится позже);
- `proportional_records`: по числу осциллограмм;
- `proportional_windows`: по числу окон;
- `balanced_sources`: одинаковый вес источников;
- `debug_small`: фиксированный малый поднабор.

### 7.4. Кэширование

Минимум:

- LRU-кэш на загруженные осциллограммы;
- ограничение по числу записей и по памяти;
- отключаемый кэш для тестов;
- логирование hit/miss на debug.

**Цель:** реализовать выводы части 2.1 до масштабного SSL, сохранив воспроизводимый legacy baseline.

### 8.1. Feature builder v2

Builder должен поддерживать:

- `symmetric_polar`: h1-h9 для токов и напряжений;
- `angle_encoding='sincos'` как Phase 5 default;
- отключение отдельных ветвей для абляций;
- одинаковый результат для разных `SPP` при одинаковом физическом сигнале в пределах численной погрешности;
- корректную обработку отсутствующих фаз/нулевых каналов;
- metadata о реально доступных гармониках.

Минимальные тесты:

- NaN propagation и masks;
- одинаковая физическая фаза при 50 и 60 Гц;
- недоступные гармоники при малом SPP.

### 8.2. Новый PhysicalStem

Текущий `PhysicalStem` предполагает пары `(magnitude, raw_angle)` и потому несовместим напрямую с `magnitude + sin + cos`. Для Phase 5 нужен отдельный stem/version, а не скрытая смена смысла входов.

Предлагаемая структура:

1. `PhasePolarEncoder`: фазные признаки, сохраняющие индивидуальность фаз.
2. `SymmetricPolarEncoder`: последовательности всех стандартных гармоник.
3. `LowFrequencyContextEncoder`: низшие гармоники/медленная динамика.
4. `ComplexInteractionBlock`: физические операции только после восстановления нормализованного комплексного представления из `sin/cos`.
5. Fusion/gating трёх ветвей в `d_model` с сохранением masks.

Необходимо пересмотреть:

- `DirectionalRelayGate`: принимать циклическое представление или вычислять `cos(phi - mta)` напрямую из `sin/cos`, не восстанавливая угол через неустойчивую границу;
- `ComplexMultiheadAttention`: raw-angle dot product заменить на циклически корректное сходство, например через dot product нормированных `(sin, cos)`;
- `AmpOnlyLayerNorm`: адаптировать к структуре `amplitude | directional_embedding`, а не предполагать, что вторая половина — сырой угол;
- `DataSanitizer`: применять missing token до образования валидной единичной пары `sin/cos`;
- физический блок мощности: при необходимости использовать сопряжение тока/напряжения явно, чтобы операция соответствовала выбранному определению комплексной мощности.

## 9. Этап 5: Phase 5 SSL pretrain

**Цель:** обучать модель без учителя на реальных данных.

В основной SSL-поток входят все пригодные цельные осциллограммы Open_EE и French/RTE независимо от наличия будущей PDR/OZZ-разметки. Исключение известных ОЗЗ требуется для формирования `real_no_OZZ` в supervised-задачах, но не для общего SSL: аварийные и неаварийные процессы одинаково полезны как неразмеченные физические режимы. Но удаление этих real_no_OZZ не будем пока что проводить, ибо это не основная задача, да и их не так много + модель на этом этапе будет учиться другому. Да, не совсем корректное действие, но и LLM учат почти на всём, а потом проверяют на конкретном, что могло всё же когда-то встречаться.

Новый скрипт:

- `scripts/phase5_experiments/run_phase5_pretrain.py`

Он должен наследовать стиль Phase 4:

- ручной блок констант внизу файла;
- CLI overrides;
- `--smoke`;
- `--resume`;
- `--reset-optimizer`;
- `latest_checkpoint.pt`;
- `best_model.pt`;
- `config.json`;
- `training_log.jsonl`;
- экспорт кривых.

### 9.1. Pretext tasks

Базовый набор:

- masked spectral-temporal modeling: скрываем часть временных зон/физических групп и восстанавливаем спектральные признаки;
- реконструкция phase-polar и symmetric-polar ветвей с раздельными метриками;
- прогноз будущих зон, если текущая архитектура стабильно это держит;
- consistency между фазным и симметричным представлением одного физического сигнала;
- опционально contrastive/consistency-задача между разными augmentations одной осциллограммы, но только после базовой стабильности.

Не надо сразу превращать Phase 5 в архитектурный зоопарк. Первое качество фазы — надёжная инфраструктура и воспроизводимое обучение.

### 9.2. Loss

База:

- оставить `SpectralReconstructionLoss`/`ComplexMSELoss` как старт;
- проверить работу при `NaN` каналах;
- логировать компоненты loss отдельно: current, future, masked, per-channel group.

Исследовать улучшения:

- Huber/SmoothL1 поверх комплексной ошибки для устойчивости к выбросам;
- амплитудно-фазовый loss с раздельными весами;
- относительная ошибка с нижним порогом шума, как в Phase 4;
- channel-balanced loss, чтобы отсутствующие/малые каналы не ломали масштаб;
- curriculum: сначала h1 и базовые гармоники, затем расширенный спектр.

### 9.3. LR scheduler

Проблема не в “косинусной функции потерь”, а в управлении скоростью обучения. В Phase 5 нужен выбор scheduler, который реагирует на процесс.

Поддержать:

- `cosine_warmup` как legacy baseline;
- `cosine_warm_restarts`;
- `reduce_on_plateau` по `val_loss`;
- `onecycle` для коротких прогонов;
- `warmup_plateau_decay`: warmup -> plateau monitoring -> decay;
- логирование фактического LR каждую эпоху.

Стартовая рекомендация:

- для длинного SSL: warmup + `ReduceLROnPlateau` или warmup + cosine restarts;
- для коротких smoke/ablation: `OneCycleLR`;
- early stopping по умолчанию выключить, потому что запуск ручной и долгий, но предупреждения о стагнации логировать.

### 9.4. Validation

Validation-набор должен быть стабильным:

- фиксированный seed;
- фиксированный список осциллограмм/окон;
- отдельно Open_EE-val и French-val;
- общая val-метрика и per-source метрики;
- сохранение нескольких реконструкций в отчёт/PNG для визуального контроля.
- небольшой frozen-backbone PDR linear probe после контрольных checkpoint, чтобы SSL не оптимизировался только под удобную реконструкцию.

А в коде надо будет делать защиту. Чтобы ПО не падало у других пользователей, а прост выдавала предупреждение и за «лучшую», брала любую из доступных)

Для каждого органа зафиксировать (примечание автора: Возможно скорректируем, когда появится описание первых моделей):

- идентификатор и версию алгоритма;
- используемые величины: фазные или прямой последовательности h1;
- источник поляризующего напряжения/тока;
- текущие величины и величины `t-200 ms`, если орган адаптивный;
- угол максимальной чувствительности и зона действия;
- амплитудные уставки, блокировки, выдержки и hysteresis;
- требования к наличию каналов;
- единицы, нормировку и направление знаков;
- форму выхода: binary start/trip, continuous margin, angle margin, confidence;
- поведение при NaN и недостаточной предыстории.

Реализация:

- общий интерфейс `PDRAlgorithm`;
- чистые векторизованные функции без зависимости от PyTorch Dataset;
- конфигурации органов отдельно от кода;
- unit-тесты на аналитических фазорах и граничных углах (примечание автора: Стоит быть аккуратной с функциями относящимися к коммерческой тайне);
- trace/debug output, объясняющий причину действия органа.

### 11.2. Статистическое исследование органов

Конкретный протокол статистики определить после получения математики, но инфраструктура должна уметь считать:

- долю срабатываний по источникам/объектам/режимам;
- распределения рабочих величин и margins;
- согласие между органами;
- случаи, где органы расходятся;
- устойчивость к изменению уставок (примечание автора: И надо будет указать, какие из них изменяемы, ибо далеко не все есть смысл менять на практике, поэтому изменяемы лишь некоторые у каждой из версий);
- время первого действия (примечание автора: В целом полезно, но в рамках этого исследования не очень нужно, скорее касается реальной РЗА, например для задач ОЗЗ); и стабильность решения;
- зависимость от отсутствующих каналов и качества напряжения;
- отдельные статистики по Open_EE и French, учитывая разные классы напряжения и нормировку.

Нельзя выбирать лучший орган только по числу срабатываний. До появления независимой разметки критерий выбора должен объединять физическую корректность, устойчивость, согласованность и ручную проверку выборки спорных случаев. (примечание автора: Но выберу по чём делать псевдоразметку я сам из личного опыта. Так что глубокого изучения по этой статистики о том, какая версия лучше, вряд ли получится сделать. Это надо будет по эталонным данным делать уже потом);

### 11.3. Псевдоразметка реальных данных лучшим органом

После решения исследователя о teacher-алгоритме:

1. прогнать его по пригодным Open_EE и, если физически сопоставимо, French-записям;
2. формировать метку для последней точки каждого 10-периодного окна (примечание автора:  Это будет плавающее окно, так что размечена будет почти каждая точка в итоговых файлах);
3. дополнительно сохранять непрерывные диагностические величины и confidence/margin;
4. сохранять `teacher_id`, версию, конфиг и hash входной осциллограммы;
5. не смешивать train/val окна одной осциллограммы;
6. по возможности разделять не только по файлам, но и по объектам/родственным режимам (примечание автора: пока что этого не будет, максимум по исходным датасетам).

Эта разметка является **weak/pseudo-label**, а не независимой истиной. Поэтому нужны:

- hard-label режим для уверенных примеров (примечание автора: будет добавлен позже);
- soft targets или sample weights по margin/confidence;
- игнорирование пограничных/неопределённых точек;
- отдельный набор расхождений нескольких органов для последующего исследования;
- frozen teacher benchmark: нейросеть должна сравниваться с органом, который создал метки.

### 11.4. Первое PDR fine-tuning

Основная постановка:

- вход: последовательность спектральных токенов за 10 периодов;
- выход: решение в последней точке (`last_state`), опционально короткая конечная область;
- входной минимум для classical PDR probe: h1 прямой последовательности U/I либо фазные h1;
- полный Physical KAN получает также остальные гармоники и low-frequency context, чтобы исследовать полезность дополнительной информации;
- сравнить random init, frozen SSL backbone, частично размороженный и полный fine-tuning;
- сравнить `sequence` и `snapshot_pair` (примечание автора: писал, что скорее всего будет 3 варианта содеражие 2 точки, 5 точек и, если обучение не будет слишком тяжёлым, то версия с прореживанием 1/8);
- исследовать auxiliary regression по margin/рабочей величине, а не только бинарную BCE.

### 11.5. Пост-обучение на сложных случаях

После обучения на псевдоразметке собрать отдельный high-quality dataset:

- сложные случаи, сгенерированные в RTDS;
- вручную доразмеченные COMTRADE;
- случаи расхождения аналитических органов;
- ложные/пограничные срабатывания teacher;
- режимы с пропавшими каналами, насыщением ТТ, помехами и коммутациями.

Форму разметки определить совместно с исследователем. Предпочтительно хранить не только класс, но и:

- направление;
- факт пуска/блокировки;
- доверие эксперта;
- интервал неопределённости;
- тип сложного режима;
- при наличии — непрерывную целевую рабочую величину.

Стратегии пост-обучения для сравнения:

- обычный fine-tuning на смеси pseudo/high-quality;
- curriculum: простая pseudo-разметка -> сложные случаи (примечание автора: скорее всего будут лишь случаи с разметкой, без указания сложностей и т.д., всё же силы и ресурсы на задачу пока что не такие большие);
- пониженный вес pseudo-label после появления качественной разметки;
- replay простых режимов для защиты от catastrophic forgetting;
- distillation/regularization относительно SSL backbone или teacher только там, где teacher надёжен.

### 11.6. Итоговое сравнение PDR

Сравнить:

- все реализованные аналитические органы;
- teacher-орган;
- модель после pseudo-label fine-tuning;
- модель после post-training;
- random-init neural baseline;
- компактный baseline только на `U1/I1 h1` и двух snapshots (примечание автора: Или прорежение разработанной модели, ибо хочется сделать модель, которой будет посильно использовать в текущих устройствах РЗА).
- (примечание автора: и ещё мысль на подумать - орган без уставок хорошо, но он становится совсем не регулируемым, а даже наши адаптивные немного регулируются, задаётся порог чувствительности по ТТ, активируются некоторые функции и т.д. Надо будет хотя бы осмыслить это по итогам созданной модели и подумать над тем, как можно бы решить / улучшить этот вопрос, иначе в непредвиденных случаях / сложных объектах орган становится бесполезным, так как нельзя исправить его косяки. ## 17. Главные риски

1. **Open_EE уже нормализован.** Повторная нормировка через `norm_coef_all_v1.4.csv` испортит масштаб.
2. **French current nominal неизвестен.** Нельзя молча выбрать делитель по максимуму КЗ. Сначала RMS/квантили, затем ручное решение.
3. **Разные SPP.** Нужно batch grouping или padding/mask, иначе обучение станет нестабильным и тяжёлым по VRAM.
4. **Огромные CSV.** Нельзя использовать pandas/polars так, чтобы файл целиком попадал в RAM.
5. **Слишком ранняя конвертация всего архива.** Сначала прототип shards и benchmark чтения.
6. **Смешение pretrain и fine-tuning источников.** SimOZZ не должен незаметно попасть в SSL как “реальные данные”.
7. **Неправильный real_no_OZZ.** Из Open_EE надо исключить известные ОЗЗ по отчёту, иначе normal-класс будет загрязнён.
8. **Слом Phase 4.** Все новые адаптеры должны добавляться рядом, без разрушения текущих скриптов.
9. **Сырой угол в модели.** Линейная обработка `angle` создаёт искусственный разрыв около `-pi/pi`; Phase 5 contract должен использовать циклическое представление.
10. **Слепое следование части 2.1.** Статья исследовала supervised-классификацию при 1600 Гц, а Phase 5 включает SSL, PDR и разные SPP; новый контракт нужно подтвердить абляциями.
11. **Teacher leakage.** Оценка PDR на псевдоразметке того же аналитического органа измеряет прежде всего способность копировать teacher, а не улучшение защиты.
12. **Наследование ошибок teacher.** Пограничные решения должны иметь confidence/margin и не считаться безусловной истиной.
13. **Domain shift PDR.** French — сеть другого класса напряжения и типа заземления; применение одних PDR-формул/уставок требует физического обоснования.
14. **Утечка между окнами.** Split делается по осциллограммам, объектам и группам родственных режимов, а не по случайным окнам.
15. **Catastrophic forgetting при post-training.** Сложные случаи не должны уничтожить поведение на обычных режимах; нужен replay/смешанный контроль.

## 18. Стартовые решения по умолчанию

- Open_EE/French weights для первого полного pretrain: `0.667 / 0.333`.
- Окно: 10 периодов.
- Stride: 1/8 периода.
- Open_EE storage: shards по 100 осциллограмм после benchmark (но это стоит обдумать).
- French storage: оставить `DATA_S.npz`, использовать adapter.
- French voltage normalization: `value * 18.310 / (90000 * 3)` (проверить).
- French current normalization: после RMS-отчёта, параметр задаётся явно.
- Missing channels: `NaN`.
- Phase 5 features: `feature_contract_v2`, symmetric-polar h1-h9 + phase-polar branch + отдельная low-frequency branch, фазы через `sin/cos`.
- Legacy Phase 4 features: `feature_contract_v1`, только для совместимости и baseline.
- PDR output: `last_state` по последней точке 10-периодного окна; `snapshot_pair` — обязательный компактный baseline.
- PDR pseudo-labels: хранить teacher version, margin/confidence и маску неопределённых случаев.
- OZZ: task adapter сохраняется, но не блокирует путь data -> feature v2 -> SSL -> PDR.
- Scheduler для первого длинного SSL: warmup + `ReduceLROnPlateau` или warmup + cosine restarts; выбор зафиксировать после smoke.
- Early stopping: выключен, но логировать стагнацию.
- Main style: ручные константы + CLI как в Phase 4.
