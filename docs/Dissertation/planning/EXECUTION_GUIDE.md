# Как выполнять план по одной задаче

Этот документ превращает общий план в последовательность небольших проверяемых работ. Сейчас выполняется только планирование: наличие карточки не означает, что описанная в ней работа уже сделана или что автор поручил выполнить все этапы сразу.

## Что читать исполнителю

1. `../AGENTS.md` и `DECISIONS.md` — ограничения и уже принятые решения.
2. [Очередь задач](TASK_BOARD.md) — состояние, зависимости и следующая работа.
3. Только нужную карточку из [переноса](RUNBOOK_MIGRATION.md), [объединения материалов](RUNBOOK_INTEGRATION.md) или [завершения диссертации](RUNBOOK_COMPLETION.md).
4. Последний отчёт по выбранной задаче и названные в карточке входные файлы. Общий `MIGRATION_PLAN.md` читать для контекста этапа, не загружать все статьи одновременно.

Все пути в карточках относительно `docs/Dissertation/`, кроме явно указанных `docs/...` от корня репозитория и абсолютных внешних путей. Будущие пути означают, что файл надо создать в соответствующей задаче; его отсутствие до этого нормально. Не создавать заранее пустые «готовые» отчёты.

## Как выбрать задачу

Если автор указал ID, выполнять его при завершённых зависимостях. Иначе взять первую доступную задачу по порядку строк очереди. `A01` — первая задача для нового исполнителя. Если есть собственная незавершённая задача, сначала продолжить её по отчёту, проверив состояние файлов.

Задача доступна, когда все ID в колонке «После» имеют статус `DONE`, входы существуют и относятся к нужной версии. Отсутствие входа записать как конкретный блокер; не угадывать его содержание. `TODO` с выполненными зависимостями можно перевести в `READY` самостоятельно. Контрольная точка — проверка фактов и качества, а не обязательный запрос разрешения автора.

Выполнение одной задачи по стартовому промпту означает одну конкретную карточку либо одну её дочернюю задачу. Не переходить автоматически от переноса к научной правке. Если автор поручил целый этап, последовательно выполнить все доступные задачи этого этапа; граница карточки сама по себе не повод остановиться посреди порученного этапа.

## Размер задачи

Одна задача должна иметь обозримый вход и результат: один небольшой подраздел, одна сложная таблица/формула, один пакет до 10 замечаний или одна карточка статьи. Для текстового переноса ориентир — до 3–5 исходных страниц или 20–40 обычных абзацев; это верхний ориентир, а не требование разрывать смысл или объект. Сложный объект выделять отдельно.

Большие карточки помечены «повторяемая». До их выполнения раскрыть их в дочерние задачи с конкретными границами: `B03-001`, `B03-002`, `C02-AI-01` и т. п. Список брать из фактического реестра блоков/источников. В каждой дочерней карточке указать точные ID входных блоков, путь результата, зависимости и проверки. Не поручать слабому исполнителю «перенести главу целиком» без такого разбиения.

Родительская задача становится `DONE`, только когда выполнены все дочерние задачи и проверено покрытие всего её входного списка. Родитель не является зависимостью собственных детей; дети наследуют внешние зависимости родителя. Последовательные дети, меняющие один файл, зависят от предыдущего ребёнка. Проверку суммарного покрытия включать в последний дочерний отчёт.

## Состояния и доказательства

| Статус | Когда использовать |
|---|---|
| `TODO` | Задача ещё не начата; возможно, ждёт предшественников |
| `READY` | Все входы и зависимости доступны |
| `DOING` | Указаны исполнитель, сессия и область изменяемых файлов |
| `REVIEW` | Результат создан, но проверки или исправления ещё не закончены |
| `DONE` | Все критерии карточки выполнены, приведены файлы и результаты проверок |
| `BLOCKED` | Есть конкретный неустранимый в этой задаче недостаток входа, доступа или авторского решения |

Сам факт запуска скрипта, наличие PDF или фраза «проверено» не основание для `DONE`. Нужны команда/метод, ожидаемый и фактический результат, путь к отчёту. Если визуальная проверка не выполнена, так и записать; не заменять её текстовым извлечением.

Проверку может выполнить тот же исполнитель отдельным проходом от критериев приёмки и исходника. Не требуются отдельный агент или новая сессия ради формального согласования. Сложные научные противоречия передавать автору с цитатами и вариантами, не разрешать догадкой.

## Рабочий цикл

1. Прочитать карточку и последний отчёт. Проверить ID источника, его SHA-256 и актуальность зависимостей.
2. Проверить локальные инструкции и текущие изменения Git. Не откатывать чужие изменения. Для Word/PDF и других форматов прочитать соответствующий доступный навык перед такой работой.
3. Зафиксировать `DOING` и точные файлы, которые будут изменены. Для повторяемой карточки сначала создать дочерние строки и карточки по шаблону.
4. Выполнить нумерованные шаги, ограничившись входным блоком. Новый научный вопрос записать отдельно с источником и продолжать независящую от него работу.
5. Сверить результат с исходником, затем пройти критерии карточки. Не оценивать только собственный пересказ.
6. Исправить выявленные дефекты и повторить затронутую проверку. Не расширять работу на соседнюю главу без необходимости.
7. Сохранить `planning/handoffs/<ID>.md` по [шаблону](TASK_TEMPLATE.md), обновить очередь и при необходимости журнал решений.
8. Сообщить автору ID, полученный результат, проверки и следующий доступный ID. При незавершённости указать точный шаг продолжения.

## Передача и возобновление

Хранить состояние в файлах, а не только в чате. Не менять на `DONE` задачу, прерванную из-за времени/контекста: оставить `DOING` с отчётом о частичном результате. Другой исполнитель сначала проверяет сохранённые файлы и продолжает с указанного шага. Для `BLOCKED` указать минимально нужный вход и какие независимые задачи доступны.

Пример полезного продолжения: «B03-007: перенесены блоки DISS-005-B0041–B0048; таблица O0026 не сверена. Открыть исходник по locator из objects.json, сравнить объединённые ячейки, затем повторить сборку». Неполезно: «Почти всё готово, продолжить работу».

При изменении принятого входа не удалять старый отчёт. Записать новую версию/хеш, вернуть зависимые проверки в `TODO` или `REVIEW` и перечислить затронутые задачи. Пересчитывать только затронутые результаты, а не начинать весь проект заново.

## Где хранить доказательства

- Реестры переноса: `migration/mapping/`; извлечённые материалы: `migration/extracted/<source_id>/<sha256>/`.
- Проверки: `migration/checks/` для переноса, `review/checks/` для содержательной правки.
- Пакеты статей после точного переноса: `sources/<source_id>/<version>/`, карточки: `planning/sources/`.
- Сырые замечания: `review/raw/<source_id>/<sha256>/`; решения: `review/issues/`.
- План интеграции: `planning/integration/`; будущие сведения о внедрении: `planning/implementation/`.
- Локальные промежуточные сборки: `build/`; принятые выпуски: `releases/<release_id>/` с манифестом.

`source_inventory.json` — исходный предварительный снимок, его не перегенерировать поверх как способ показать прогресс. Новые измерения сохранять отдельно с датой и хешем. Сырые выгрузки не перезаписывать, если они отличаются: создать новую версию и описать причину.

## Как не потерять смысл при техническом переносе

Сохранение без изменений означает сохранение содержания, порядка и исходных объектов, а не одинаковые страницы Word и LaTeX. Если нужна техническая замена представления (например, поле на метку), записать исходное значение, новую связь и основание. При отслеживаемой правке хранить оба варианта и разметку; показывать вставку/удаление в контрольном представлении, не выбирать за автора окончательный текст.

Единая базовая запись блока содержит `block_id`, `source_id`, `source_sha256`, `story_part`, `locator`, `source_order`, `kind`, `raw_text`, `target_path`, `target_label`, `status`. `locator` должен находить объект в неизменном пакете (например, XPath с индексами), а не только цитату, которая может повторяться. Порядок обхода и индексацию описать в реестре. ID после выдачи не перенумеровывать.

Объекты получают `object_id`, `block_id`, тип, исходный номер/подпись, положение/relationship, файл или XML-фрагмент, SHA-256 при наличии файла, целевой путь/метку, способ переноса и проверку. Один медиафайл может использоваться несколько раз: учитывать и уникальные файлы, и каждое размещение. Вспомогательная таблица оформления не равна научной таблице.

## Ошибки и безопасное продолжение

| Ситуация | Действие |
|---|---|
| Хеш исходника отличается | Не обновлять ожидаемый хеш автоматически; сохранить сведения о новой версии, найти прежний снимок, выяснить происхождение различия |
| Нет компилятора или рендера | Завершить доступную инвентаризацию, записать диагностику; не выдавать непроверенный перенос за готовый |
| Конвертер потерял формулу/комментарий | Выделить объект, сохранить исходник и XML/изображение, восстановить проверяемым способом; до сверки задача остаётся незавершённой |
| Две статьи дают разные значения | Записать обе ссылки, условия и версии; не усреднять и не выбирать автоматически более красивое значение |
| Источник не найден | Сохранить явный пробел и точные реквизиты поиска; не придумывать библиографическую запись |
| Нет документа о внедрении | Описать подтверждённый статус и запросить конкретный недостающий документ; не формировать фиктивный акт |
| Задача слишком велика | Разбить по входным ID и зависимостям; не уменьшать объём молчаливым пропуском |

Не нужен новый вопрос автору по поводу каждой папки, ID или технического файла. Вопрос нужен, когда требуется неизвестный авторский факт, научный выбор, отсутствующий документ или разрешение, которое не следует из поручения. Отсутствие ответа не является решением.
